# 新载板网络恢复与上报验证（2026-10-31）

本文记录 2026-10-31 对 W5500 网络链路的恢复过程、已确认结果和仍未完成的
验收项。

## 一、启动阻塞根因

启用网络后板端曾停在 HardFault，GD-Link 实测：

```text
CFSR=0x01000000  UNALIGNED
HFSR=0x40000000  FORCED
```

构建配置同时启用了单核 `CONFIG_UP=y` 和 `CONFIG_SPINLOCK=y`。NuttX Kconfig
明确说明单核配置使用 spinlock 很可能致命。关闭 `CONFIG_SPINLOCK` 后，板端
可以稳定启动并保留网络功能。

## 二、W5500 初始化调整

- 关闭 NSH 启动阶段的自动 `ifup`。
- 将 W5500 驱动注册从板级 bringup 移到 `fireeye_net_init()`。
- 启用 `W5500_POLL_FALLBACK=1`，由轮询路径补充 RX 事件。

调整后串口和本地监测先启动，网络初始化不再阻塞 NSH。

## 三、网络实测结果

电脑 Realtek 网口直连 W5500：

```text
电脑地址：192.168.1.100/24
开发板地址：192.168.1.200/24
Link：100 Mbps
Ping：4/4 成功，0% 丢包
RTT：约 5–12 ms
```

板端 HTTP POST 到达 `fireeye_monitor.py`：

```text
[13:08:35] fireeye-01 I=-0.0 A  T=22.7 C  state=NORMAL
```

网页 `/api/latest` 返回设备、电流、温度、母线电压、采样曲线和事件数据，页面
卡片与曲线可以正常显示。该结果证明 W5500 的 SPI、MACRAW、收发、静态路由和
TCP HTTP 上报链路均在工作。

启动日志中的 `PHYCFGR=0xB8` 是初始化阶段的诊断读数；在 Link 已建立后仍出现
过该值，但实际 Ping 和 HTTP 均通过，因此不能只凭该次读数判定物理层失败。

## 四、长时间上报停滞与修复

后续观察到板端主循环仍运行，但网页数据停止更新。原上报线程每 5 秒新建 TCP
连接，`connect/send/recv` 没有应用层超时，且只预分配 8 个 TCP 连接。上游响应
异常或连接未及时回收时，上报线程可能长期阻塞。

已加入以下修复：

- 非阻塞 `connect`，3 秒连接超时；
- `send/recv` 3 秒超时；
- TCP 短写循环处理；
- 异常后立即关闭 socket；
- 上位机响应显式发送 `Connection: close`；
- TCP 预分配连接数提高到 16；
- 每 12 次成功上报输出一次低频心跳。

该修复已完成编译和补丁可应用性检查，仍需烧录后执行至少 5 分钟持续上报测试。

## 五、网络与保护仍需验收

- 5 分钟以上持续 HTTP 上报和断线恢复。
- 1.2A WARNING、1.5A ALARM 与继电器断载。
- NTC 接插件间歇性异常。
- 路由器/跨网段环境；当前结论仅覆盖电脑与开发板静态地址直连。

## 六、电流精度观察与校准接口

2026-10-31 晚将电源设为约 `6.00 V / 0.114 A / 0.685 W`，同时通过 COM4
读取板端周期数据。连续多个周期的板端结果稳定在：

```text
I=0.13 A
T=24.8～25.0 C
Vbus=5.6 V
state=NORMAL
```

网页同期数据从 `0.12 A / 5.56 V` 收敛到 `0.13 A / 5.56～5.62 V`。考虑到
两位小数的量化范围，板端真实电流仍约为 `0.125～0.135 A`，相对电源读数高出
约 10%～18%，因此不能只用显示精度解释。电源输出端与 INA228 VBUS 测量点之间
约有 `0.4 V` 压差，涉及 SS54、继电器、接插件和线路，不能直接把 `5.6 V` 与
`6.00 V` 当作同一测量点比较。

已新增 2.1.0 诊断构建：

- 串口周期行和 `fireeye current` 输出 `raw20`、`raw20` 的母线值和四位小数；
- HTTP、网页、事件、报告和 CSV 提高精度；
- 新增 `CONFIG_FIREYEYE_CURRENT_CAL_GAIN_PPM`；
- 新增 `CONFIG_FIREYEYE_CURRENT_CAL_OFFSET_UA`；
- 默认仍为 `gain_ppm=1000000`、`offset_uA=0`，没有提前写死经验修正。

该构建已编译并生成 HEX/BIN，但尚未烧录，因此本节结论仍是“原始换算存在偏差，
校准待验证”，不能表述为校准已经完成。

2026-11-01 对已烧录的 2.1.0 做网页和网口完整测试时，初始 Ping、HTTP 上报、
网页、CSV、AI 风险和 AI 事件报告均可工作；随后网页时间戳停在 `ts=274`，
连续 60 秒的 12 次页面轮询均未更新，PC 侧 Ping 4/4 失败，ARP 状态为
`Unreachable`。同期串口仍持续输出 `FireEye` 周期数据，说明主采样循环没有死机，
故障位于网络子系统。

针对该现象已构建 2.1.1：socket 保持非阻塞，HTTP 发送和接收都通过
`poll(POLLOUT/POLLIN)` 提供 3 秒硬超时，避免阻塞调用长期持有网络锁。该版本
尚未烧录，因此不能把 2.1.1 的持续网络稳定性记为通过。

首次烧录 2.1.1 后，串口只出现本地初始化和 OLED 日志，没有 `FireEye net`
输出，网页因此显示设备未连接。核对发现该镜像的派生 `config.h` 丢失了
`CONFIG_NET`、`CONFIG_NET_W5500` 和 `CONFIG_FIREYEYE_NET`。已从保留的完整
配置恢复网络栈，并重新生成包含 W5500、16 个 TCP 预分配连接和 1.2A/1.5A
阈值的镜像。该修正版仍需重新烧录后测试。
